##### Steps to reproduce

The file `typescript-client-test/models/Errors.ts` generated is faulty: `Array&lt;ModelError&gt;FromJSON`

```ts
export function ErrorsFromJSONTyped(json: any, ignoreDiscriminator: boolean): Errors {
    if (json == null) {
        return json;
    }
    return {        
        'errors': json['errors'] == null ? undefined : Array&lt;ModelError&gt;FromJSON(json['errors']),
    };
}
```

and 

```ts
export function ErrorsToJSONTyped(value?: Errors | null, ignoreDiscriminator: boolean = false): any {
    if (value == null) {
        return value;
    }

    return {
        
        'errors': Array&lt;ModelError&gt;ToJSON(value['errors']),
    };
}
```

## Comment by Mattias-Sehlstedt on 2025-08-02

Hi,

Could you provide a source for the expectations that the current array definition should be considered a proper definition? My current understanding is that if you want to define an array that is a defined object together with a new property then you would do so as 

```
{
  type: array  
  items: 
    type: object
     properties:
       error_schema_with_property: ...
       error_ref: $ref
    }
}
```
I.e., you have to define it as an inline object with two properties. See [this](https://swagger.io/docs/specification/v3_0/data-models/data-types/#arrays) as a source for an array of something that is not a ref.

## Comment by Mattias-Sehlstedt on 2025-08-18

The project is structured so that a specification is first interpreted into a Java representation within an OpenAPI class (done with [swagger-code](https://github.com/swagger-api/swagger-core)/swagger-parser). It is then normalized, where "oddities" and concepts that can be expressed in a simpler manner are converted. Then it is converted into a codegen representation, which expresses common attributes that can act as hooks for code concepts. This is then used in a mustache template which in turn becomes the generated code.

I would suggest investigating where the issue arises by debugging how the [normalizer](https://openapi-generator.tech/docs/customization/#openapi-normalizer) handles the odd array-schema (e.g., by creating a [unit-test](https://github.com/OpenAPITools/openapi-generator/blob/master/modules/openapi-generator/src/test/java/org/openapitools/codegen/OpenAPINormalizerTest.java#L33) for it).

It is also possible to implement and inject your own Normalizer into the gradle task with `NORMALIZER_CLASS` if you were to find how the issue should/could be handled. But the preferred solution would of course be if the project could handle this for everyone.
